# v0.1.0 release signing + verification

The `v0.1.0` source tarball (the `directjob-scout-0.1.0.tar.gz`
artefact attached to the GitHub Release — pre-rename identity-of-record
at sign time; see "Project rename note" below) is cryptographically
signed with [cosign](https://docs.sigstore.dev/cosign/overview/).
This page documents the verification commands a downstream
re-distributor or NLnet reviewer can run.

## Project rename note (2026-05-19)

On 2026-05-19 the project was renamed from **DirectJob Scout** to
**Helpmefindthejob** ([Decision 22](../grant/04-research-and-decisions.md#decision-22-project-rename--directjob-scout--helpmefindthejob)).
The v0.1.0 release shipped before the rename, so the cosign signature
was computed over the bytes of `directjob-scout-0.1.0.tar.gz` (the
pre-rename identity-of-record). The SHA-256 in the table below is the
content hash of those specific bytes. To keep verification working
post-rename, **the maintainer attaches the original signed tarball as
a release asset under its original filename** — verifiers download the
asset directly by name rather than via GitHub's
`--archive=tar.gz` auto-generated archive (whose top-level directory
would now be `helpmefindthejob-0.1.0/` rather than the signed
`directjob-scout-0.1.0/`, producing different bytes and a different
SHA-256).

## Verifying

You need `cosign` installed locally — see
<https://docs.sigstore.dev/cosign/system_config/installation/>.

```bash
# 1. Download the original signed tarball + cosign bundle + public key
#    from the GitHub Release. NOTE: download the asset by name (do NOT
#    use --archive=tar.gz post-rename — that produces a different
#    archive whose bytes won't match the signed SHA-256).
gh release download v0.1.0 \
  --pattern 'directjob-scout-0.1.0.tar.gz' \
  --pattern 'v0.1.0-source.tar.gz.sigstore' \
  --pattern 'v0.1.0-cosign.pub'

# 2. Verify the signature.
#    --insecure-ignore-tlog is required because the v0.1.0 signing
#    uses a long-lived key (model b in the slice plan); the key was
#    NOT registered with the Sigstore transparency log. Future
#    releases (v0.2.0+) plan to switch to keyless via GitHub Actions
#    OIDC at which point the transparency-log check applies and the
#    flag goes away. See "Future releases" below.
cosign verify-blob directjob-scout-0.1.0.tar.gz \
  --key v0.1.0-cosign.pub \
  --bundle v0.1.0-source.tar.gz.sigstore \
  --insecure-ignore-tlog
```

Expected output:

```
WARNING: Skipping tlog verification is an insecure practice that
lacks transparency and auditability verification for the blob.
Verified OK
```

The "Skipping tlog verification" warning is **expected** for v0.1.0
specifically — see "Signing-key model" below. The "Verified OK"
line is the contract.

If `Verified OK` does NOT appear, the tarball has been altered or
the signature does not match the public key. Treat the artefact as
untrusted and contact the maintainer via the GitHub Security
Advisories link in `SECURITY.md` (or the
[`security.txt`](https://maksodf.github.io/helpmefindthejob/.well-known/security.txt)
Contact list).

## Signing-key model

Helpmefindthejob v0.1.0 uses **cosign model (b) — long-lived ECDSA
P-256 key pair**, generated locally on the maintainer's
workstation. The private key (`cosign-v0.1.0.key`) is stored
outside the repo in `~/.config/helpmefindthejob/`, protected by
`chmod 600` + an encrypting password. The public key is committed
at `docs/releases/v0.1.0-cosign.pub` AND attached to the GitHub
Release — two pinning points so a verifier doesn't depend on a
single retrieval surface.

### Why not keyless / Sigstore-OIDC for v0.1.0?

cosign supports a **keyless** workflow (model a) that uses GitHub
Actions OIDC tokens to sign and registers the signature in the
Sigstore Rekor transparency log. Keyless has stronger trust
properties — the signer is provably the GitHub Actions workflow
identity, no private key needs to be managed by humans, and the
transparency log makes after-the-fact tampering impossible.

We're deferring keyless for v0.1.0 for one reason: keyless requires
running the sign step inside GitHub Actions, which means
constructing + landing a Release workflow first. The grant-sprint
time-box for v0.1.0 favoured shipping the signed artefact via the
long-lived key now over waiting for the workflow. **v0.2.0+ is
planned for keyless** — the Release workflow is on the post-grant
roadmap.

### Key rotation

The current key is for v0.1.0. Future releases SHOULD generate a
fresh key (or switch to keyless). Don't reuse this key for v0.2.0
+; rotating per-release narrows the blast radius if a key is ever
compromised.

When generating a new key:

```bash
cd /tmp/cosign-keygen
COSIGN_PASSWORD="<strong random password>" cosign generate-key-pair
mv cosign.key ~/.config/helpmefindthejob/cosign-<version>.key
chmod 600 ~/.config/helpmefindthejob/cosign-<version>.key
mv cosign.pub <repo>/docs/releases/<version>-cosign.pub
```

Then sign with the per-version key and commit + upload the per-
version `.sigstore` bundle + public key. The previous-version
public key stays in the repo for historical-release verifiability.

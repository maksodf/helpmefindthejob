## Audit-log hardening (#13)

| # | Item | Effort | Target |
|---|---|---|---|
| 13 | ~~**Audit-log tamper-evidence (HMAC-chain substrate)**~~ — **CLOSED 2026-05-21 at the substrate level**. Centralised log forwarding is operator-side infrastructure (deferred). Substrate shipped: (a) every emitted audit-log record now carries `sequence_no` (1-indexed monotonic) + `chain_hmac` (HMAC-SHA256 keyed by deployer salt, over `prev_chain_hmac || canonical_record`); (b) `AuditLogEmitter` loads `(last_sequence_no, last_chain_hmac)` lazily on first write by scanning current + rotated log files (chain runs across rotations so deletion of a rotated file is detectable as a sequence gap); (c) new public `verify_chain(log_paths, salt) -> ChainVerificationResult` walks records in sequence-number order and returns a structured pass/fail report covering: missing-sequence-no, sequence-gap (caught as `missing_sequence_numbers`), hmac-mismatch, malformed-json, file-read-error. Wrong-salt input rejects every record at sequence 1 (an attacker with file-write access but no salt cannot forge a valid chain). The canonical-record HMAC EXCLUDES `chain_hmac` itself (chicken-and-egg) but INCLUDES `sequence_no` (so reordering records on disk fails to defeat verification — although verify_chain explicitly sorts by sequence_no, so simple in-file reordering is benign by design; the integrity claim is sequence-number monotonicity, not file order). +13 contract tests at `tests/test_audit_log_tamper_evidence_13.py` (stamping / verify-happy-path / 5 tampering scenarios / chain across rotations + emitter resumption / wrong-salt). 1791 → 1804 tests.
